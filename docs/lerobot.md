# LeRobot이란 무엇인가

> 작성 2026-09-10. 이 문서는 "무엇을 하는 라이브러리인가"보다 **"왜 이런 구조가 필요했는가"**에
> 초점을 둔다. 코드 확인 없이 개념 정리 목적으로 쓴 문서라, 구체적인 API 시그니처는
> 실제 레포(`huggingface/lerobot`)에서 다시 확인할 것.

## 한 줄 정의

**LeRobot은 실물 로봇 학습(real-world robot learning)을 위한 HuggingFace의 통합 라이브러리다.**
데이터셋 포맷 · 정책(policy) 구현 · 학습 루프 · 실물 로봇 드라이버 · 평가까지를
하나의 코드베이스 안에 넣었다. NLP에서 `transformers`, 비전에서 `timm`이 했던
"파편화된 구현을 하나의 인터페이스로 모으는" 역할을 로보틱스에서 하려는 시도다.

## 왜 이런 게 필요했나 — 로보틱스 ML의 파편화 문제

비전/NLP와 달리 로보틱스는 최근까지 **공유 가능한 추상화가 없었다.**

| 층위 | NLP | 로보틱스 (LeRobot 이전) |
|---|---|---|
| 데이터 | `datasets`, 텍스트/토큰으로 통일 | 랩마다 rosbag, HDF5, RLDS, 자체 pickle… |
| 모델 | `transformers`, `from_pretrained` | 논문마다 독립 레포, 재현 스크립트도 제각각 |
| 하드웨어 | 없음 (필요 없음) | 로봇 팔·그리퍼·카메라마다 별도 SDK |
| 평가 | 벤치마크 스코어 | 실물 롤아웃 — 표준화 자체가 어려움 |

문제의 핵심은 **모달리티 다양성**이다. 하나의 에피소드에 RGB 여러 대, 관절 상태,
그리퍼 상태, 힘/토크, 언어 지시, 그리고 시간축이 얽혀 있다. 게다가 카메라와 관절
인코더의 **샘플링 주파수가 다르고 타임스탬프가 어긋난다.** 이걸 "그냥 텐서 하나"로
못 다루기 때문에, 각 랩이 자기 포맷을 만들었고 코드 재사용이 거의 불가능했다.

LeRobot의 베팅은 이렇다: **데이터 포맷을 먼저 통일하면 나머지(정책, 학습, 평가)가
따라온다.** 그래서 라이브러리의 중심에 모델이 아니라 `LeRobotDataset`이 있다.

## 핵심 구성요소

### 1. `LeRobotDataset` — 설계의 중심

에피소드 단위 로봇 데이터를 담는 표준 포맷. 설계상 중요한 결정들:

- **영상은 비디오로, 나머지는 테이블로.** 이미지 프레임을 PNG로 풀어놓지 않고
  mp4로 인코딩해서 저장한다. 관절 상태·액션 같은 저차원 신호는 parquet 테이블.
  이유는 단순히 용량이다 — 로봇 데이터셋은 프레임 수가 수백만 단위이고,
  개별 이미지 파일로 두면 저장 공간과 파일시스템 inode 양쪽에서 터진다.
  대신 랜덤 액세스 시 디코딩 비용을 지불하게 되므로, 데이터로더의 병목이
  대개 GPU가 아니라 **비디오 디코딩**이 된다. (튜닝 지점으로 기억할 것)
- **타임스탬프가 1급 시민.** 프레임 인덱스가 아니라 시간 기준으로 정렬되고,
  `delta_timestamps`로 "현재 기준 -0.1초, 0초, +0.1초 프레임을 함께 달라"는
  요청을 표현한다. 이게 있어야 관측 히스토리(observation stack)와
  **액션 청크(action chunk)**를 데이터셋 레벨에서 깔끔하게 뽑을 수 있다.
  ACT / Diffusion Policy / π0 계열이 전부 "한 스텝이 아니라 앞으로 N스텝을
  한 번에 예측"하는 구조라 이 기능이 필수다.
- **HF Hub에 그대로 올라간다.** 데이터셋이 Hub 리포지토리이므로
  `LeRobotDataset("lerobot/<name>")` 한 줄로 남의 로봇 데이터를 받는다.
  이게 커뮤니티 데이터셋이 쌓이는 실질적 동력이다.

### 2. 정책 (Policies)

정책은 `select_action(observation) -> action` 인터페이스를 공유한다.
크게 두 계열:

- **VLA 계열 (VLM 백본 + 액션 헤드):** Pi0 / Pi0-FAST / Pi0.5, SmolVLA,
  GR00T N1.7, XVLA, EO-1 등. 사전학습된 비전-언어 모델을 물려받아
  언어 지시를 이해하고, 그 위에 연속 액션을 출력하는 헤드를 붙인다.
- **스크래치 학습 계열:** ACT(Action Chunking Transformer),
  Diffusion Policy, VQ-BeT. VLM 없이 해당 태스크 데모만으로 학습한다.
  가볍고 빠르게 도는 **베이스라인**으로서 가치가 크다.

> 학습 순서 제안: ACT로 "모방학습 파이프라인이 도는 것"을 먼저 체감하고,
> 그 다음 π0 계열로 넘어가는 게 디버깅 난이도상 훨씬 낫다.

액션을 어떻게 표현하느냐가 이 분야의 핵심 갈림길이다:

| 방식 | 대표 | 성격 |
|---|---|---|
| 연속값 회귀 | ACT | 단순, 멀티모달 분포 표현이 약함 |
| 이산 토큰화 | OpenVLA, Pi0-FAST | LM 어휘 재사용, 시퀀스가 길어짐 |
| 벡터 양자화 | VQ-BeT | 토큰이되 학습된 코드북 |
| 흐름/확산 | Diffusion Policy, π0 | 멀티모달 분포에 강함, 샘플링 비용 |

### 3. 실물 로봇 레이어

`lerobot`이 다른 학습 라이브러리와 결정적으로 다른 지점.
저가형 로봇 팔(SO-100/SO-101, Koch, ALOHA 등)의 드라이버와
**텔레오퍼레이션 → 데이터 기록 → 학습 → 롤아웃**의 전 사이클이 CLI로 들어있다.
"학습 라이브러리"가 아니라 "로봇 실습 스택"인 이유다.

시뮬레이션 환경(gym-aloha, gym-pusht 등)도 붙어 있어서, 하드웨어 없이도
파이프라인 전체를 돌려볼 수 있다. **우리 상황에서는 여기부터 시작한다.**

### 4. 학습/평가 스크립트

`lerobot-train`, `lerobot-eval` 류의 엔트리포인트가 설정 기반(dataclass config)으로
동작한다. 정책 교체가 설정 한 줄이 되도록 만든 구조라, 비교 실험이 쉽다.

## 전형적인 워크플로

```
1. 데이터 확보    Hub에서 pull  또는  텔레오퍼레이션으로 직접 기록
2. 정책 선택      ACT / Diffusion / SmolVLA / π0 ...
3. 학습           lerobot-train  (사전학습 VLA면 파인튜닝)
4. 평가           시뮬 롤아웃 → 성공률 / 실물 롤아웃
5. 배포           체크포인트를 Hub에 push, 추론 서버로 서빙
```

## 이 프로젝트에서의 위치

- 로컬 Mac에서는 **읽기와 문서화만.** 모델 실행 없음 (`CLAUDE.md` 참조).
- 실행은 학교 연구실 GPU 서버에서. 첫 목표는 시뮬 환경 + ACT로
  파이프라인 한 바퀴를 완주하는 것.
- `openvla`는 액션 토크나이저와 RLDS 파이프라인 **독해용 레퍼런스**로만 둔다.
  LeRobot과 달리 자체 스택을 통째로 가지고 있어서 섞어 쓰지 않는다.
